## ⚡ Performance

- [x] `loadGenerationBatch` (formerly `loadPokemons`) fetches each Pokémon's full detail **and** its species data individually per batch (up to 60 requests for a 30-item batch) — was previously uncached. Fixed as part of centralizing the API client ([src/api/pokeapi.js](src/api/pokeapi.js)): every request now goes through an in-memory cache keyed by URL, so re-fetching the same species/Pokémon/type (e.g. revisiting a generation, favoriting something already seen elsewhere, opening the same Pokémon's detail twice) no longer hits the network twice. This is per-session/in-memory only, not persistent across reloads — a persistent cache (e.g. via the service worker or IndexedDB) is still a possible future improvement.
- [x] No `<img>` `width`/`height` attributes on Pokémon sprites/type icons ([Pokedex.js](src/components/Pokedex/Pokedex.js)) — risks layout shift, contradicting the README's claimed CLS < 0.1. Fixed: card sprites (100×100), favorite-chip sprites (36×36) and the type icons in [TypeFilterModal.js](src/components/TypeFilterModal/TypeFilterModal.js) (24×24) now carry `width`/`height` matching their CSS sizes, so space is reserved before the stylesheet loads. The CSS still controls the rendered size (e.g. 72px cards on mobile). The CLS < 0.1 claim itself hasn't been measured.
- [x] Service worker precache list ([public/sw.js](public/sw.js)) was static and didn't include the hashed JS/CSS bundle filenames Vite produces on build — the very first offline visit after install wouldn't have the app shell cached. Fixed with the same `swBuildManifest` plugin in [vite.config.js](vite.config.js) (no Workbox dependency needed): it injects every file under `assets/` (hashed bundles) and `types/` (filter icons) into the precache list of the built `sw.js`. The same work uncovered a second bug: `caches.match` respected `Vary: Origin`, which hosts commonly send, but Vite's `crossorigin` script/link tags add an `Origin` header that the cached requests didn't have — so cached bundles never matched and the app shell never loaded offline. Lookups now use `ignoreVary: true`. Verified against `vite preview`: after install, a fresh offline load renders the full styled app shell. PokéAPI responses are still not cached (the SW only caches same-origin responses), so Pokémon data itself isn't available offline.
- [x] `CACHE_NAME` in [sw.js](public/sw.js#L4) was hardcoded (`pokedex-v1`) with no build-time versioning — every deploy needed someone to remember to bump it manually or stale caches persisted indefinitely. Fixed with a small `swBuildManifest` plugin in [vite.config.js](vite.config.js) that replaces a `__BUILD_HASH__` placeholder in the built `sw.js` with a hash of the rest of the build output. The name only changes when a built file actually changes, and the build fails if the placeholder goes missing. In dev the placeholder stays literal, giving one fixed dev cache name.

## 📲 PWA

Goal: an installed app that updates reliably, works offline for anything you've already seen, and behaves like a native app (back button, deep links, share).

**Updates & service worker** ([sw.js](public/sw.js), [registerSW.js](src/registerSW.js))

- [x] **Updates never take over.** A new deploy installs a new service worker, but with no `skipWaiting()`/`clients.claim()` and no update UI it sits in "waiting" until every window of the app is closed. Installed users can stay on an old version for days. Detect `registration.waiting` / `updatefound`, show an "Update available · Reload" [Toast](src/components/Toast/Toast.js), and on tap `postMessage` the waiting worker to `skipWaiting()` and reload on `controllerchange`. Also check for updates on `visibilitychange`, not only hourly. — [sw.js](public/sw.js) now has a `message` handler that calls `self.skipWaiting()` on `{type: 'SKIP_WAITING'}`, and its `activate` handler calls `self.clients.claim()` so an already-open tab is actually handed the new worker. [registerSW.js](src/registerSW.js) was rewritten around this: it reports an already-`waiting` or newly-`installed` worker via an `onUpdateAvailable(worker)` callback, `applyUpdate(worker)` posts the skip-waiting message, and a `controllerchange` listener reloads the page once (guarded so a stray second event can't reload twice). It also now checks for updates on `visibilitychange` becoming visible, in addition to hourly. A new [useServiceWorkerUpdate](src/hooks/useServiceWorkerUpdate.js) hook wraps this for React and is wired through `App.js` → `Pokedex.js`, which shows the "A new version is available" Toast with a Reload action once `updateAvailable` flips true. Tested directly: [registerSW.test.js](src/registerSW.test.js) (registration, already-waiting vs. newly-installed detection, single reload on controllerchange, no-support/registration-failure paths) and [useServiceWorkerUpdate.test.js](src/hooks/useServiceWorkerUpdate.test.js) (the callback → state → reload wiring).

  Verifying this live (headless Chrome against `vite preview`, via CDP) surfaced two real bugs the unit tests, written around the same mistaken assumptions, didn't catch: (1) `registerSW()` waited for `window`'s `load` event, safe for the old "plain `<script>` at the bottom of the page" pattern but not when called from a React effect - a fast-loading page can fire `load` _before_ the effect runs, so the listener is added too late and registration never happens at all (confirmed live: `navigator.serviceWorker.register` was never called). Fixed by registering immediately when `document.readyState === 'complete'`. (2) `clients.claim()` fires `controllerchange` on a page's _first_ install too (no controller → one), not just on a real update - the original one-time `hadController` snapshot, taken before that first claim, stayed `false` for the rest of that page's life, so a genuine later update (tab left open) would never reload either. Fixed by tracking `hadController` across events instead of snapshotting it once. Also simulated a full deploy live (build A open in a tab, rebuild to build B, apply the update): the toast appears with the right text, `registration.waiting` is detected, and clicking Reload successfully applies `skipWaiting()` (confirmed via `registration.waiting` going from true to false and the new worker reaching `activated`) - but whether `controllerchange` then fires for that already-open tab (and so the page actually reloads) was inconclusive in this scripted/CDP-driven setup specifically; every SW-side step that should cause it (skipWaiting, activate, cache cleanup, `clients.claim()`) was independently confirmed to run. This narrow piece - does the open tab really reload itself once you click Reload - still wants a check on a real deploy/real browser, which the "Audit it" item below already calls for.
